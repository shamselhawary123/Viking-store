# Product Variants + Inventory Progressive Migration Plan

Status: design checkpoint only. No production code, migration, RLS, checkout, or admin UI changes have been made.

## Current Architecture Found

- Existing product pages load `products` with `categories`, `product_colors(product_images)`, and `product_sizes`.
- Existing admin product create/edit writes:
  - product-level `products.price` / `products.old_price`
  - color/image options in `product_colors` / `product_images`
  - size availability in `product_sizes.in_stock`
- Cart line identity is currently `product.id + color name + size`.
- Checkout sends product-level cart items to `create_checkout_order`.
- Checkout RPC recalculates price from `products.price`, creates `orders`, creates `order_items`, and supports coupons.
- Checkout currently has no variant ID, no stock locking, and no inventory decrement.
- `/shop` and product cards use `products.price`; this should remain the compatibility/minimum active variant price for variant products.
- The repo does not contain the original schema migration for `products`, `product_colors`, `product_sizes`, `orders`, or `order_items`.

## Important Existing Type Drift

- Recent product ordering work treats `products.id` as `bigint`.
- The checkout coupon RPC still casts product IDs to `integer` in `build_checkout_items`.
- Before writing final SQL, confirm live column types for:
  - `products.id`
  - `product_colors.id`, `product_colors.product_id`
  - `product_sizes.id`, `product_sizes.product_id`
  - `orders.id`
  - `order_items.product_id`

Recommended verification SQL:

```sql
select table_name, column_name, data_type, udt_name, is_nullable
from information_schema.columns
where table_schema = 'public'
  and table_name in (
    'products',
    'product_colors',
    'product_sizes',
    'product_images',
    'orders',
    'order_items'
  )
order by table_name, ordinal_position;
```

## Target Model

- `products.inventory_model`: explicit mode, either `legacy` or `variants`.
- Existing products must be backfilled to `legacy`.
- New products should be explicitly created as `variants` by the future admin UI; the database default remains `legacy` for backward safety.
- `product_variants` is the sellable inventory entity:
  - `id bigint generated by default as identity primary key`
  - `product_id bigint` references `products(id)`
  - nullable `color_id bigint` references `product_colors(id)`
  - nullable `size_id bigint` references `product_sizes(id)`
  - `price numeric not null`
  - `stock_quantity integer not null default 0`
  - `active boolean not null default true`
  - timestamps
- Color images stay on `product_colors` / `product_images`.
- Variant stock drives availability for variant products.
- `products.price` remains compatibility price and should be synced to min active variant price.
- Legacy products continue using `product_sizes.in_stock` and `products.price`.

## Phase Plan

### Phase 1: Schema + Compatibility Only

Goal: add the data model without changing live behavior for existing products.

Tests first:
- migration contains `products.inventory_model`
- existing products are backfilled to `legacy`
- database default remains `legacy`
- `product_variants` has price/stock/active constraints
- no auto-conversion from legacy rows to variants
- `products.price` sync function only affects `inventory_model = 'variants'`

Migration contents:
- add `products.inventory_model`
- backfill existing rows to `legacy`
- set the database default to `legacy`
- create `product_variants`
- add admin/public RLS policies for variants
- create trigger/function to sync `products.price` from active variants
- do not alter checkout/order behavior yet
- do not create variants for existing products

Stop after Phase 1 and report final migration SQL for review. Do not apply it live.

### Phase 2: Admin Product Variant Management

Goal: allow new products to be managed with variants while preserving legacy edit behavior.

- Admin can choose/manage color, size, price, stock per variant.
- Legacy products remain editable in the existing legacy UI unless explicitly migrated later.
- New products use `inventory_model = 'variants'`.
- Admin UI should prevent saving a variant product without at least one active variant.
- No automatic conversion of the 62 existing products.

### Phase 3: Storefront Variant Selection

Goal: product pages support both legacy and variant inventory models.

- Legacy products keep current color/size behavior.
- Variant products select a real variant before add-to-cart.
- Cart line identity becomes variant-aware.
- Product cards and listing still use `products.price`.
- No per-card review/variant overfetching.

### Phase 4: Secure Checkout Inventory

Goal: database-authoritative order creation with inventory decrement.

- Extend checkout RPC payload to support `variant_id` for variant products.
- RPC locks selected variants with `FOR UPDATE`.
- RPC validates active variant, stock, product, price, coupon eligibility, and quantity.
- RPC decrements stock only after validation and in the same transaction as order creation.
- `order_items` stores `variant_id` if the existing schema can accept it; otherwise add a nullable FK after review.
- Legacy checkout remains supported during migration.

### Phase 5: Optional Manual Legacy Migration

Goal: admin-controlled migration of individual legacy products only.

- No automatic conversion.
- Provide a tool/UI path to create variants from existing size/color combinations.
- Admin explicitly switches product from `legacy` to `variants` after review.
